# SSabway

역 안에서 GPS가 끊겨도 길을 잃지 않도록, 안내 표지판을 촬영하면 AI가 위치를 인식해 목적지까지 안내하고, 막히면 역무원과 화상으로 연결하는 실내 길안내 서비스입니다.

## 1. 왜 만들었나

지하철 역사 안에서는 GPS 신호가 잡히지 않아 지도 앱이 무력해집니다. 특히 한국어를 모르는 외국인이나 길찾기가 어려운 이용자에게 환승·출구 찾기는 큰 장벽입니다. SSabway는 이 문제를 표지판 인식, 경로 안내, 화상 상담 세 축으로 풉니다.

| 이용자가 겪는 문제 | SSabway의 해결 |
|------|------|
| 실내에서 GPS가 안 잡힌다 | 역 안내 표지판을 촬영하면 AI(YOLO+ResNet)가 41종 중 위치를 인식 (실전 정확도 92.9%) |
| 어디로 어떻게 가야 할지 모른다 | 역 내부를 73개 노드·106개 엣지 그래프로 모델링, 다익스트라로 역 내 최단 경로와 대중교통 환승 경로를 안내 |
| 그래도 길을 잃었다 | 버튼 하나로 역무원과 실시간 화상 상담(WebRTC) 연결 |
| 한국어를 모른다 | 4개국어(한/영/일/중) 전면 지원 |
| 촬영 화면에 남이 찍힌다 | 통화 영상의 얼굴을 브라우저에서 실시간 픽셀화한 뒤 발행 — 원본 프레임은 서버로 나가지 않음 |

GitLab push 시 Jenkins가 EC2·Docker로 자동 빌드/배포하고, SSabway API 서버(Spring Boot)와 Signaling API 서버(OpenVidu)를 Nginx가 프록시합니다. 표지판 인식은 FastAPI(AI) 서버가, 경로·장소 검색은 외부 API(ODsay·지도)가 담당합니다.

전송 방식은 데이터 성격에 따라 나눴습니다.

| 데이터 | 프로토콜 | 이유 |
|------|------|------|
| 음성·영상 | WebRTC (SFU) | 손실을 감수하더라도 지연이 낮아야 한다 |
| 얼굴 좌표 · 번역 자막 | WebSocket | 손실보다 순서와 신뢰성이 중요하다 |
| 그 외 도메인 데이터 | REST | — |

프론트엔드는 User App과 Admin App 두 개의 앱으로 나누고, 인증·WebRTC·i18n 등 공통 로직은 `shared` 레이어로 분리했습니다.

```
frontend/src
├── user/     # 사용자 앱  (촬영 → 경로 안내 → 화상 상담)
├── admin/    # 관리자 앱  (상담 응대 · 내역/민원 · 블랙리스트)
├── shared/   # webrtc · caption · api · station-map · pwa · ui  (두 앱 공통)
├── locales/  # ko · en · ja · zh
└── mocks/    # MSW 핸들러  (백엔드 병렬 개발)
```

의존성 방향은 `user → shared`, `admin → shared` 단방향만 허용합니다. `user`에서 `admin`을 import하면 코드 스플리팅이 조용히 깨지고 관리자 코드가 사용자 번들에 합쳐집니다.

## 5. 트러블슈팅

### 5-1. 대역폭을 아끼려다 모자이크가 통째로 꺼진 문제

통화 영상의 얼굴은 브라우저 canvas에서 픽셀화한 뒤 발행하고, 얼굴 좌표는 검출용 프레임을 WebSocket으로 AI 서버에 보내 받습니다. 그런데 이 프레임 전송이 통화 영상과 **같은 업링크**를 씁니다. 대역폭을 줄이려고 검출 프레임 해상도를 낮췄더니, 어느 지점부터 검출이 아예 잡히지 않았습니다. 더 나쁜 건 그 결과였습니다. 검출이 0이면 서버가 빈 배열을 돌려주고, 클라이언트는 그것을 "얼굴 없음"으로 해석해 **모자이크를 완전히 해제**합니다. 절감하려던 최적화가 미가림 영상을 그대로 내보내고 있었습니다.

감으로 정할 수 없다고 판단해, 실제 역 사진 120장으로 해상도 4단계를 직접 측정했습니다.

| 검출 프레임 긴 변 | 검출 성공 |
|------:|------:|
| **1280px** | **34 / 120** |
| 960px | 12 / 120 |
| 640px | 4 / 120 |
| 320px | **0 / 120** |

표지판을 비추는 화면이라 주변 사람이 멀리 작게 찍히고, 축소하면 얼굴이 몇 픽셀로 뭉개져 사라집니다. 같은 실험에서 **JPEG 품질(0.6 ↔ 0.3)은 검출률에 영향이 없다**는 것도 확인했습니다.

그래서 해상도는 1280px로 유지하고 검출률과 무관한 품질만 0.35로 낮춰, 프레임당 **113KB → 79KB(30% 감축)** 로 해상도를 올린 비용을 되돌려 받았습니다. 전송 주기도 초당 4장에서 2.5장(400ms)으로 낮춰 약 264KB/s 선에 맞추고, 400ms 지연으로 박스가 뒤처지는 만큼은 사방 15% 여유로 흡수했습니다.

여기에 **fail-closed** 구조를 기본값으로 뒀습니다. 검출 소켓이 죽었을 때 얼굴이 그대로 나가는 것이 이 기능의 최악의 실패라고 정의하고, 2초간 응답이 없으면 화면 전체 픽셀화로 후퇴하도록 했습니다(`STALE_MS = 2000`). 첫 검출 결과가 도착하기 전 초기값도 `protectAll = true`입니다. "검출 불가 = 전부 가림"을 기본 방향으로 두어 미가림 영상 유출을 구조적으로 차단했습니다.

측정 결과와 **"낮추려면 반드시 다시 측정하라"** 는 경고는 상수 옆 주석으로 남겨, 다음 사람이 성능을 이유로 해상도를 낮추지 못하게 했습니다.

### 5-2. 모바일 첫 로드에서 JS의 70.9%를 지연 로드로 뺀 코드 스플리팅

지하철역 지하, 저품질 회선에서 첫 화면이 떠야 하는 서비스입니다. 그런데 하나의 Vite 프로젝트에 사용자 앱과 관리자 앱이 함께 있어, 그대로 두면 모바일 이용자가 역무원 전용 코드와 WebRTC 라이브러리까지 받게 됩니다.

|  | raw | gzip |
|------|------:|------:|
| 빌드 JS 전체 | 1,618,548 B | 500,164 B |
| 사용자 첫 로드 JS | 470,642 B | 138,947 B |
| **지연 로드로 뺀 양** | **1,147,906 B (70.9%)** | **361,217 B (72.2%)** |

빼낸 것은 admin 청크 697,125 B와 openvidu-browser 435,238 B입니다. 이 분리는 설정 하나로는 성립하지 않고 **네 개가 한 세트**로 맞물립니다.

1. `manualChunks` — `src/admin/` 코드를 별도 청크로 분리
2. `React.lazy` — admin 라우트와 화상 상담 페이지만 동적 import
3. `workbox.globIgnores` — 두 청크를 서비스워커 precache에서 제외
4. `navigateFallbackDenylist` — `/admin` 경로를 SW 폴백에서 제외

하나만 바꾸면 조용히 깨지므로, 이 의존 관계와 검증 방법(`dist/sw.js`의 precache 목록 확인, preview에서 Network 탭 확인)을 주석과 문서로 남겼습니다.

PWA precache는 **8개 파일 / 547,673 B(534.8 KiB)** 로, `dist` 전체 14.4MB의 **3.79%** 입니다. 사용법 안내 애니메이션 12.7MB(webp)를 의도적으로 제외했기 때문입니다. 설치형 앱이니 전부 캐시한다는 기본 반사를 따르면, 사용법을 보지 않는 이용자도 첫 방문에 12.7MB를 받게 됩니다. 대신 지하 약전파 구간을 전제로 **표지판 이미지는 런타임 CacheFirst**(최대 300장 / 30일)로 따로 캐싱합니다.

여기서 중요한 판단은 **빼지 않은 쪽**이었습니다. 사용자 라우트 12개는 일부러 lazy로 분리하지 않았습니다.

> `user` 앱은 메인 청크에 포함시켜야 PWA 오프라인 진입이 보장된다. `admin`만 lazy로 분리한다.
> — `app/router.tsx`

지하에서 네트워크가 끊긴 채 앱을 다시 열었을 때 청크를 받아올 수 없으면 화면 자체가 뜨지 않습니다. 반대로 화상 상담 페이지는 유일하게 lazy로 뺐는데, openvidu-browser를 끌고 오는 데다 **통화 자체가 네트워크 없이는 성립하지 않아** 오프라인 보장 대상이 아니기 때문입니다. "최적화 = 무조건 잘게 쪼개기"가 아니라, 어떤 화면이 오프라인에서 떠야 하는지를 기준으로 나눴습니다.

### 5-3. 사용자와 관리자가 동시에 토큰을 재발급할 때 생기는 충돌

액세스 토큰 만료 시 401을 받아 재발급하고 원 요청을 재시도하는 인터셉터를 구현했습니다. 동시에 여러 요청이 401을 받으면 재발급이 중복되므로 보통 `let refreshPromise: Promise | null` 하나로 묶는데, 이 서비스에는 **한 브라우저에서 사용자와 관리자가 동시에 로그인될 수 있다**는 조건이 있었습니다.

Promise를 하나로 합치면, 두 역할이 거의 동시에 재발급할 때 뒤에 온 쪽이 앞의 Promise를 그대로 받습니다. 그러면 **자기 슬롯에는 토큰이 없는데 성공을 돌려받아** 이후 요청이 계속 401을 맞습니다. 그래서 재발급 Promise를 `Record<AuthRole, Promise<string> | null>` 로 역할별 슬롯으로 나눴습니다.

같은 맥락에서 처리한 것들:

- **역할 불일치 토큰 차단** — 재발급받은 JWT의 `type` 클레임을 요청한 역할과 대조해, 다른 역할의 토큰이 들어오면 거부합니다.
- **403의 두 종류를 분리** — 시큐리티 단계의 거부(`code === 'FORBIDDEN'`)만 로그인 만료로 처리하고, 블랙리스트·상담 권한 같은 업무 거부는 고유 코드를 그대로 화면에 전달합니다. 이 분기가 없으면 역무원이 남의 대기를 눌렀다는 이유로 로그아웃되는 동작이 나옵니다.
- **인터셉터 무한루프 방지 3층** — 재발급·로그아웃은 인터셉터가 없는 `bareClient`로 호출하고, 비로그인 공개 API는 `publicApi`로 분리하고, 그래도 남는 경로는 `NO_RETRY_PATHS`로 명시 제외했습니다.

### 5-4. STT 비용을 줄였더니 자막이 확정되지 않던 문제

번역 자막은 통화 오디오를 서버로 보내 STT와 번역을 거칩니다. Azure는 **처리한 오디오 시간으로 과금**하므로 아무도 말하지 않는 구간까지 보내면 통화 시간 전체가 청구됩니다. 상담에서 한 사람이 실제로 말하는 시간은 절반이 안 되므로, RMS 기준 `0.008` 이하인 조각을 버리는 무음 게이팅을 넣었습니다. 비용이 줄고 잡음 구간이 빠져 인식 품질도 좋아졌습니다.

그런데 자막이 **INTERIM(중간 결과)만 뜨고 FINAL(확정)이 나오지 않는** 부작용이 생겼습니다. 원인은 서버의 문장 종료 판정 방식이었습니다. Azure는 일정 시간의 침묵을 보고 문장 끝을 판단하는데(서버 설정 `SEGMENTATION_SILENCE_MS = 500`), 말이 멈추는 순간 전송도 끊어버리면 **그 침묵 자체가 서버에 도착하지 않습니다.**

발화가 끝난 뒤에도 서버 판정 시간보다 넉넉히 긴 `TAIL_MS = 900` 동안은 조용한 조각도 계속 보내도록 해서, 비용 절감과 문장 확정을 양립시켰습니다.

오디오 추출에는 `MediaRecorder` 대신 `AudioWorklet`을 썼습니다. `MediaRecorder`의 timeslice 방식은 **두 번째 조각부터 컨테이너 헤더가 없어** 조각 단위 스트리밍에 쓸 수 없기 때문입니다. AudioWorklet으로 16kHz mono PCM16을 직접 추출해, 조각당 320ms / 5,120 샘플 / 10,240 B의 고정 크기 바이너리 프레임으로 보냅니다.

**화상 상담에서 두 사람의 화면이 서로 다르게 보이던 문제**

역무원이 "화면 오른쪽 표지판으로 가세요"라고 안내해도 사용자 화면엔 그 표지판이 안 보였습니다. 같은 발행 프레임을 각자 박스에 `object-cover`로 담는데, 기기마다 화면 비율이 0.46~0.56(약 20% 편차)으로 제각각이라 잘리는 범위가 달랐습니다. 모바일 주소창이 뜨고 사라질 때마다 `100dvh`가 바뀌어 비율을 상수로 고정할 수도 없었습니다.

사용자 브라우저가 자기 박스 비율을 실측해 OpenVidu 시그널로 역무원에게 전송하도록 했습니다. 문제는 입장 순서 경합이었는데, 시그널은 그 순간 접속한 참가자에게만 가므로 양방향으로 값을 밀고, 역무원은 리스너를 먼저 붙인 뒤 요청해 응답 유실을 없앴습니다. 값이 못 와도 통화가 유지되도록 기본 비율 폴백을 뒀습니다.

**상담 중 새로고침 한 번에 상담 정보가 사라지던 문제**

역무원이 수락한 상담 정보(이메일·출발지·목적지·언어)를 라우팅 state로 넘기고 있었는데, 새로고침이나 뒤로가기를 하면 정보가 조용히 사라져 화면이 깨졌습니다. 블랙리스트 등록 시 user-info 반환 에러로 처음 드러났습니다.

화면 간 데이터 전달을 Zustand `persist`(sessionStorage) 스토어로 옮기고, 상담 종료 시 `clearDetail()`로 명시적으로 비워 다음 상담 정보와 섞이지 않도록 생명주기를 관리했습니다. 이 패턴을 세션·상담 정보 전반에 팀 방침으로 통일했습니다.

**카메라 권한을 거부하면 막다른 페이지에 갇히던 문제**

권한을 거부하면 별도의 "권한 없음" 페이지로 이동해 되돌아올 길이 없었습니다. 막다른 페이지를 없애고 실패 원인을 권한 거부와 그 외 오류로 분기해, 권한 거부는 촬영 화면을 유지한 채 4개국어 토스트로 안내하고 즉시 재시도할 수 있게 했습니다.

**재촬영해도 이전 사진이 뜨던 이미지 캐시 문제**

브라우저가 같은 이미지 URL을 캐시해, 표지판을 다시 촬영해도 이전 이미지가 그대로 떴습니다. 이미지 URL에 버전 쿼리스트링을 붙여 캐시를 무효화(cache-busting)했습니다.

**국내 접속 시 첫 화면이 한국어로 뜨던 i18n 기본 언어 문제**

주 타깃이 외국인이라 선택 전 기본값은 영어여야 하는데, `LanguageDetector`가 브라우저 언어를 감지해 국내 접속이면 `ko`가 기본값을 덮어썼습니다. 감지 소스를 `localStorage`만 보도록 제한하고 `lng` 명시를 제거해 저장값이 없을 때 `fallbackLng`(영어)로 떨어지게 했습니다. `nonExplicitSupportedLngs`로 `en-US`·`zh-TW`도 각각 `en`·`zh`에 매칭시켰습니다.

### 팀원 간 이해가 달라 개발이 어긋나던 문제

팀 전원이 협업이 처음이었습니다. 초기에 와이어프레임을 다 같이 제대로 검토하지 않은 채 작업을 시작했고, 기능을 어떻게 동작시킬지에 대한 이해와 소통이 부족했습니다. 여기에 API 명세서가 제대로 작성되지 않아 요청/응답 형식이 서로 달라, 프론트-백엔드 연동 단계에서 어긋남과 재작업이 반복됐습니다. Frontend 담당으로 화면·API 접점이 가장 많아 이 문제가 제게 직접 드러났습니다.

구현에 들어가기 전에 와이어프레임을 함께 다시 짚어 팀이 같은 화면을 보게 하고, 각자 이해한 동작·데이터 흐름이 실제로 일치하는지를 말로 되짚어 확인하는 과정을 도입했습니다. 특히 API 계약(엔드포인트·요청/응답 필드·상태 전환)을 화면 기준으로 먼저 맞춰, 명세 공백에서 오는 인식 차이를 개발 전에 제거했습니다. 연동 단계의 재작업과 머지 충돌이 줄었고, 무엇을 만들지만큼 같은 것을 이해하고 있는지를 먼저 맞추는 습관이 팀에 자리잡았습니다.

## 7. 회고

써보지 않은 기술이 많았던 프로젝트였습니다. WebRTC 세션 관리, AudioWorklet으로 PCM을 직접 뽑는 오디오 파이프라인, canvas 합성 스트림, PWA 캐싱 전략은 모두 이번에 처음 다뤘습니다. 그런데 6주를 돌아보면 기술을 익힌 것보다, 팀이 같은 것을 보고 있게 만드는 일이 훨씬 어렵고 중요했습니다.

와이어프레임은 그림이 아니라 팀이 합의한 사양입니다. 초반에 와이어프레임을 다 같이 충분히 검토하지 않은 채 각자 이해한 대로 만들기 시작했고, 개발 단계에서 화면과 API가 어긋나 재작업이 반복됐습니다. Frontend 담당으로 화면·API 접점이 가장 많아 이 비용이 제게 직접 쌓였습니다. 그래서 구현에 들어가기 전에 와이어프레임을 함께 다시 짚어 팀이 같은 화면을 보게 하고, 각자 이해한 동작과 데이터 흐름이 실제로 일치하는지 말로 되짚어 확인하는 과정을 도입했습니다. 화면이 확정된 뒤부터 개발 속도가 눈에 띄게 붙었습니다. 그리는 데 하루가 아깝다고 생각했던 문서가, 실제로는 일주일의 재작업을 막는 문서였습니다.

문서의 최신본이 무엇인지 합의하는 것 자체가 작업이라는 것도 배웠습니다. API 명세가 변경되면서 역명이 번역 표기와 한국어 표기 두 필드로 분리됐는데, 이 변경이 제때 전파되지 않아 프론트는 번역 표기를 그대로 서버에 보내고 있었습니다. 서버는 한국어 컬럼과 정확 비교하기 때문에 한국어 사용자만 상담 요청에 성공하고 영어·일본어·중국어 사용자는 전부 404를 받았습니다. 외국인 대상 서비스에서 가장 나쁜 형태의 버그였고, 개발자 로케일에서는 재현조차 되지 않았습니다. 원인은 코드가 아니라 명세서·기능명세서·와이어프레임이 여러 버전으로 흩어져 "지금 무엇이 최신인지"를 각자 다르게 알고 있던 데 있었습니다. 이후로는 명세가 바뀌면 화면 기준으로 영향 범위를 함께 짚고, 최신본이 어디 있는지를 하나로 통일했습니다.

소통은 말을 많이 하는 게 아니라 합의를 만드는 일이었습니다. 사용자의 역 내 위치를 관리자에게 넘기는 방식을 정할 때, 서버에서 표지판 이미지 URL로 역매핑하자는 안이 나왔습니다. 저는 프론트가 가진 데이터 형태를 근거로 명세 예시 네 건 중 세 건이 URL이 비어 있고, 왕복 경로에서는 같은 URL이 두 번 등장하며, 프리사인 URL이 붙으면 문자열 비교가 실패한다는 세 가지 반례를 정리해 회신했습니다. 그리고 반대로 끝내지 않고, 클라이언트가 이미 갖고 있는 단계 인덱스를 그대로 보내면 매칭 로직 자체가 사라진다는 대안을 함께 냈습니다. 지도 출발지를 GPS 기반 인근 역 탐색에서 표지판 인식 결과로 바꾸자고 제안했을 때도 마찬가지였습니다. GPS 정확도, 표지판 데이터의 활용 가능성, 기능을 유지할 때의 구현 복잡도를 놓고 백엔드 담당자와 논의한 끝에 기능을 단순화하는 쪽으로 팀 동의를 얻었습니다. 반대 의견을 낼 때 대안을 함께 내는 것이 합의를 가장 빠르게 만든다는 걸 배웠습니다.
지도는 처음에 네이버 지도 API로 시작했는데, 주 타깃인 외국인 사용자를 생각하면 다국어 환경에서 활용도가 부족하다고 봐서 Google Maps로 갈아탔습니다. 출발지도 처음엔 GPS로 현재 위치에서 인근 역을 찾는 방식이었는데, 정작 역 내부에서는 GPS 정확도가 떨어졌고 이미 AI가 표지판으로 역 정보를 인식하고 있었습니다. 그래서 GPS 기반 인근 역 탐색은 빼고, 표지판 인식 결과에 역 정보를 함께 실어 보내자고 제안했습니다. 백엔드 담당자와 GPS 정확도, 표지판 데이터의 활용 가능성, 기능을 유지할 때의 구현 복잡도를 놓고 논의한 끝에 기능을 단순화하는 쪽으로 팀 동의를 얻었습니다.

정리하면 이 프로젝트에서 얻은 것은 빠르게 만드는 능력이 아니라, 만들기 전에 맞추고 만든 뒤에 덜어내는 판단이었습니다. 기술과 외부 API가 우리 서비스에 맞는지 먼저 검증하고, 팀이 같은 문서를 보고 있는지 확인하고, 실제 흐름에 필요 없는 기능은 과감히 걷어내는 것. 다음 프로젝트에서 가장 먼저 하고 싶은 일도 코드를 짜는 게 아니라 이 세 가지입니다.
